# Professional Video Downloader Root Instructions

Use these instructions from the repository root.

## Working Style

- Act as my implementation agent. Run the necessary PowerShell, shell, Git, and validation commands yourself; do not ask me to paste commands into a terminal.
- Before each command, briefly state its purpose. After each command, inspect the output and continue from there.
- If a command fails, diagnose it, adjust the command or code, and retry.
- Ask for confirmation only before destructive actions, credential changes, external communication, or anything blocked by permissions.
- Do not claim a command or check succeeded unless you actually ran it and verified the result.
- At the end of a task, summarize the commands run, files changed, validation performed, and any remaining issues.
- Run commands from the repository root unless a task explicitly needs a different working directory.

## Repository Layout

- `professional-video-downloader.ps1` is the main script and must remain compatible with PowerShell 5.1+.
- Keep PowerShell changes in `.ps1` files compatible with the file's target runtime, and keep POSIX shell syntax limited to `install.sh`.
- `install-bootstrap.ps1` is the Windows bootstrapper.
- `install.bat` and `install.sh` are the user-facing Windows and POSIX installers.
- `professional-video-downloader.lnk` is generated by the installer and should not be hand-edited.
- `VERSION` is the version source of truth for the distribution.
- Files under `logs/` are runtime output, not source.

## Change Principles

- Inspect the repository before editing.
- Reuse existing scripts, helpers, fixtures, and workflows instead of adding new ones.
- Keep changes focused and avoid unrelated edits.
- Prefer the smallest change that satisfies the task.
- Avoid new dependencies unless the task truly requires them.
- Keep installer changes idempotent and safe to re-run.
- Preserve the existing installer logging style and output conventions when extending bootstrap scripts.
- Use the repository's existing behavior and structure as the reference point instead of introducing a new pattern unless the task clearly calls for it.

## Validation

- Prefer behavior-based validation over compile-only checks.
- Run the smallest relevant validation first, then broader checks only if they add value.
- For script changes, validate the affected entry point directly where practical.
- If the repo does not have an automated test for the change, say so and validate the script or installer path manually when possible.
- Never claim completion if required validation was skipped or failed.
- Record any skipped checks and the remaining risk.
- If you need local failure artifacts, store them under `test-artifacts/` or `test-results/` rather than cluttering the repo root.

## Versioning

- Treat `VERSION` as authoritative for the repo's version number.
- Keep `VERSION`, script headers, and user-facing docs consistent when the version changes.
- If a version bump is part of the task, update every user-visible version string that is meant to stay in sync.
- There is no repo-local version sync tool here, so version alignment is a manual step.

## Version Synchronization

The root `VERSION` file is the single source of truth for the workspace version.

- After editing `VERSION`, run `pnpm version:sync`.
- Use `pnpm version:sync:dry-run` to preview changes.
- Use `pnpm version:sync:force` in non-interactive contexts.
- `VERSIONING.md` defines the SemVer rules and supported rewrite targets.

## YAGNI

Prefer the smallest change that satisfies the current task. Add abstractions only when there is a clear current use case or when the cost of changing later is high.
